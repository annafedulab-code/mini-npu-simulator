# Mini NPU Simulator

AI가 패턴을 알아보는 핵심 계산인 **MAC(Multiply-Accumulate) 연산**을 파이썬으로 직접 구현한 콘솔 프로그램입니다.
입력 패턴과 필터(Cross, X)를 같은 위치끼리 곱한 뒤 모두 더해 점수를 구하고, 점수가 더 높은 쪽으로 모양을 판정합니다.

---

## 1. 실행 방법

**실행 환경:** Python 3.8 이상 (개발 환경: Windows 11, Python 3.14.7)
외부 라이브러리 없이 표준 라이브러리(`json`, `time`, `os`)만 사용합니다.

```bash
git clone https://github.com/annafedulab-code/mini-npu-simulator.git
cd mini-npu-simulator
python main.py
```

- `main.py`와 `data.json`이 **같은 폴더**에 있어야 모드 2가 동작합니다.

실행하면 모드를 선택합니다.

| 입력 | 모드 | 설명 |
|---|---|---|
| `1` | 사용자 입력 (3x3) | 필터 A, B와 패턴을 한 줄씩(공백 구분) 직접 입력 |
| `2` | data.json 분석 | `data.json`의 필터와 패턴을 읽어 자동으로 판정하고 PASS/FAIL 채점 |

- 실행 중 종료하려면 `Ctrl + C`를 누릅니다.

## 2. 구현 요약

### 2-1. 데이터 구조
- n×n 패턴과 필터는 2차원 리스트(리스트 안의 리스트)로 저장합니다.
- `create_matrix(n)`, `set_value()`, `get_value()`로 표를 만들고 특정 위치의 값을 저장·조회합니다.
- 3×3, 5×5, 13×13, 25×25 등 크기에 상관없이 처리할 수 있습니다.

### 2-2. 라벨 정규화
`data.json`에서는 같은 뜻의 라벨이 여러 형태로 적혀 있어, 프로그램 내부에서는 표준 라벨 `Cross`, `X` 두 가지만 사용합니다.

| 원래 값 | 위치 | 표준 라벨 |
|---|---|---|
| `+` | patterns의 expected | `Cross` |
| `cross` | filters의 키 | `Cross` |
| `x` | expected, filters의 키 | `X` |

- 앞뒤 공백 제거와 대소문자 무시 후 변환하므로 `" X "`, `"Cross"`도 올바르게 처리됩니다.
- 출력과 PASS/FAIL 비교는 모두 표준 라벨 기준으로 수행합니다.

### 2-3. MAC 연산
- `mac(pattern, filter)` 함수가 이중 반복문으로 모든 칸을 돌며 `패턴[i][j] × 필터[i][j]`를 누적해 더합니다.
- NumPy 등 외부 라이브러리를 쓰지 않고 반복문으로 직접 구현했습니다.

### 2-4. 동점 처리 정책 (epsilon)
- `abs(점수A - 점수B) < 1e-9` 이면 동점으로 보고 `UNDECIDED`(모드 1에서는 "판정 불가")로 처리합니다.
- 그 외에는 점수가 더 큰 쪽의 라벨로 판정합니다.

### 2-5. 오류 처리
- **모드 1:** 한 줄의 숫자 개수가 3개가 아니거나 숫자가 아닌 값이 있으면 안내 문구를 출력하고 그 줄을 다시 입력받습니다.
- **모드 2:** 키 형식 오류, `input`/`expected` 누락, 해당 크기 필터 없음, 필터-패턴 크기 불일치, 알 수 없는 라벨이 있으면 **그 케이스만 FAIL**로 처리하고 사유를 남긴 뒤 다음 케이스로 계속 진행합니다. 프로그램은 중단되지 않습니다.

### 2-6. 성능 측정
- 크기별로 MAC 연산만 10회 반복한 구간을 `time.perf_counter()`로 측정해 평균(ms)을 냅니다. 입력·출력·파일 읽기 시간은 포함하지 않습니다.

### 2-7. 보너스: 패턴 생성기
- `make_cross(n)`, `make_x(n)`이 크기 n만 받아 십자가/X 패턴을 자동 생성하며, 성능 분석에 이 패턴을 사용합니다.

### 2-8. 보너스 과제 1: 시뮬레이터 최적화 (메모리 접근)
- `flatten()`이 N×N 2차원 표를 길이 N²의 1차원 배열로 바꾸고, `mac_flat()`이 1차원 배열끼리 MAC 연산을 합니다.
- 성능 분석 표에서 최적화 전(2차원)과 후(1차원)를 **같은 입력, 같은 반복 횟수(10회)** 로 측정해 함께 출력합니다. 자세한 결과는 [6. 보너스 과제 1 결과](#6-보너스-과제-1-결과-2차원--1차원-최적화)에 있습니다.

## 3. 결과 리포트

### 3-1. data.json 분석 결과

| 케이스 | Cross 점수 | X 점수 | 판정 | expected | 결과 |
|---|---|---|---|---|---|
| size_5_1 | 0.9 | 0.8999999999999999 | UNDECIDED | X | FAIL |
| size_5_2 | 8.9 | 0.1 | Cross | Cross | PASS |
| size_13_1 | 0.3 | 14.700000000000008 | X | X | PASS |
| size_13_2 | 7.499999999999997 | 7.5 | UNDECIDED | Cross | FAIL |
| size_25_1 | 4.9 | 4.899999999999999 | UNDECIDED | X | FAIL |
| size_25_2 | 52.9 | 0.1 | Cross | Cross | PASS |

**총 6개 / 통과 3개 / 실패 3개**

### 3-2. 실패 원인 분석

실패 원인을 "데이터/스키마 문제", "로직 문제", "수치 비교 문제" 세 가지로 나누어 점검했습니다.

1. **데이터/스키마 문제가 아닙니다.** 6개 케이스 모두 키(`size_N_번호`)에서 크기를 정상적으로 추출했고, 필터와 패턴의 크기(5, 13, 25)가 일치하며, `input`과 `expected`가 모두 있습니다.
2. **라벨 문제도 아닙니다.** expected의 `+`, `x`와 필터 키 `cross`, `x`를 모두 `Cross`, `X`로 정규화했기 때문에 표기 차이로 인한 FAIL은 0건입니다. 정규화를 하지 않았다면 `"+"`와 `"Cross"`를 다른 값으로 보아 PASS여야 할 케이스까지 FAIL이 되었을 것입니다.
3. **로직 문제도 아닙니다.** 점수 차이가 분명한 3개 케이스(size_5_2, size_13_1, size_25_2)는 모두 정답대로 판정되었습니다.
4. **실패한 3개는 모두 수치 비교 문제, 즉 동점 케이스입니다.** 이 케이스들의 필터에는 0.9, 7.5, 4.9 같은 값이 들어 있어, 수학적으로는 두 필터 점수가 정확히 같아지도록 설계되어 있습니다.
5. 그런데 컴퓨터는 0.1, 0.3, 0.9 같은 소수를 2진수로 정확히 표현하지 못해 **부동소수점 오차**가 생깁니다. 그 결과 0.9와 0.8999999999999999처럼 아주 작은 차이(약 1e-16 ~ 1e-15)가 나타났습니다.
6. 만약 단순히 `>`로 비교했다면 size_5_1은 Cross, size_13_2는 X, size_25_1은 Cross로 판정됩니다. 셋 다 expected와 반대라서 결국 FAIL이며, 의미 없는 오차가 판정을 좌우하게 됩니다.
7. 그래서 **epsilon(1e-9) 기반 비교 정책**을 적용해 이 3개를 동점(UNDECIDED)으로 처리했습니다. 실제 오차(1e-15 수준)는 epsilon(1e-9)보다 훨씬 작으므로 동점으로 판단하는 것이 타당합니다.
8. 동점은 Cross도 X도 아니므로 expected와 같을 수 없어 FAIL로 기록했습니다. 이는 프로그램 오류가 아니라 **"구별할 수 없는 입력은 억지로 판정하지 않는다"는 정책이 의도대로 동작한 결과**입니다.
9. 판정 정확도를 높이려면 동점이 나오지 않도록 필터 값을 다시 설계해야 합니다. 비교 기준을 느슨하게 바꾸는 것은 해결책이 아닙니다.

### 3-3. 성능 분석 (평균 / 10회)

| 크기 (N×N) | 평균 시간 (ms, 2차원 `mac`) | 연산 횟수 (N²) |
|---|---|---|
| 3×3 | 0.0013 | 9 |
| 5×5 | 0.0027 | 25 |
| 13×13 | 0.0153 | 169 |
| 25×25 | 0.0573 | 625 |

※ 측정 시간은 컴퓨터 상태에 따라 실행할 때마다 조금씩 달라집니다. 1차원 최적화 후 시간은 6장에 있습니다.

### 3-4. 시간 복잡도 분석: O(N²)

1. MAC 연산은 N×N 표의 **모든 칸을 정확히 한 번씩** 방문해 곱하고 더합니다. 따라서 곱셈·덧셈 횟수는 N²입니다.
2. 코드에서도 `for row in range(n)` 안에 `for col in range(n)`이 있는 **이중 반복문**이므로 N × N = N²번 실행됩니다.
3. 그래서 시간 복잡도는 **O(N²)** 입니다. 한 변의 길이가 2배가 되면 연산량은 4배, 5배가 되면 25배로 늘어납니다.
4. 측정 결과도 이 예상과 맞습니다. 5×5에서 25×25로 갈 때 연산 횟수는 25배(25 → 625), 측정 시간은 약 21배(0.0032 → 0.0662 ms) 늘었습니다.
5. 5×5에서 13×13으로 갈 때도 연산 횟수는 약 6.8배(25 → 169), 시간은 약 5.7배로 비슷한 비율로 증가했습니다.
6. 비율이 정확히 같지 않은 이유는 함수 호출, 반복문 준비 같은 **크기와 무관한 고정 비용**이 있고, 측정 시간이 매우 짧아 컴퓨터의 다른 작업에 영향을 받기 때문입니다. 크기가 커질수록 고정 비용의 비중이 줄어 N²에 더 가까워집니다.
7. 실제 AI 모델은 수백×수백 크기의 필터를 수천 개 사용하므로, O(N²) 연산을 하나씩 순서대로 처리하는 CPU로는 감당하기 어렵습니다. 그래서 많은 MAC 연산을 **동시에(병렬로)** 처리하는 NPU가 필요합니다.

## 4. 새 라벨 확장 절차

Cross, X 외에 새 모양(예: `T`)을 추가할 때는 아래 순서를 따릅니다. 각 단계에서 무엇을 확인해야 하는지도 함께 적었습니다.

### 4-1. 1단계: 정규화 (normalize_label 업데이트)

1. `main.py` 상단에 표준 라벨 상수를 추가합니다. 예: `LABEL_T = "T"`
2. `LABEL_MAP`에 새 라벨이 data.json에 적힐 수 있는 **모든 원래 표기**를 소문자로 등록합니다. 예: `"t": LABEL_T`, `"tee": LABEL_T`
3. 기존 키(`+`, `cross`, `x`)와 **겹치지 않는지** 확인합니다. 겹치면 서로 다른 모양이 같은 라벨로 합쳐집니다.
4. 확인: `normalize_label("T")`, `normalize_label(" t ")`가 `"T"`를, 등록하지 않은 값은 `None`을 반환하는지 확인합니다.

### 4-2. 2단계: 운영 판정 (필터 로드와 판정 로직)

1. data.json의 각 `size_N` 아래에 새 필터 키(예: `"t"`)와 N×N 배열을 추가합니다.
2. `load_filters()`는 정규화된 라벨이면 자동으로 읽고, 크기가 N×N이 아니면 `x size_N.t: NxN 크기가 아니라 건너뜀`을 출력하며 건너뜁니다. 실행 화면에서 `v size_N 필터 로드 완료 (Cross, T, X)`처럼 **새 라벨이 목록에 나오는지** 확인합니다.
3. **현재 코드의 한계:** `analyze_pattern()`과 `judge()`는 Cross와 X **두 필터만** 비교하도록 작성되어 있습니다. 라벨이 3개 이상이면 아래처럼 바꿔야 합니다.
   - 해당 크기의 모든 필터로 MAC 점수를 구합니다.
   - 가장 높은 점수의 라벨을 판정 결과로 합니다.
   - 1등과 2등의 점수 차이가 `EPSILON`보다 작으면 `UNDECIDED`로 처리합니다. (기존 동점 정책 유지)
4. 어떤 크기에 새 필터가 없으면 그 크기의 패턴은 비교 대상이 달라지므로, **모든 크기(size_5, 13, 25)에 같은 라벨 세트**를 넣는 것을 원칙으로 합니다.

### 4-3. 3단계: 테스트 절차 (예상값 검증)

1. data.json `patterns`에 새 라벨을 정답으로 하는 케이스를 크기별로 1개 이상 추가합니다. 예: `"size_5_3": {"input": [...], "expected": "t"}`
2. 모드 2를 실행해 새 케이스가 `판정: T | expected: T | PASS`로 나오는지 확인합니다.
3. **기존 케이스의 결과가 바뀌지 않았는지** 확인합니다. 현재 기준은 총 6개 중 통과 3개, 실패 3개(size_5_1, size_13_2, size_25_1 동점)입니다.
4. 오류 케이스도 확인합니다.
   - 등록하지 않은 라벨을 expected에 넣으면 `알 수 없는 expected 라벨` 사유로 FAIL이 나와야 합니다.
   - 새 필터의 크기를 일부러 틀리게 넣으면 로드 단계에서 건너뛰고, 해당 크기 패턴은 `필터를 찾을 수 없음` 사유로 FAIL이 나와야 합니다.
5. 모든 확인이 끝나면 README의 라벨 정규화 표(2-2)에 새 라벨을 추가합니다.

## 5. 대규모(1000×1000) 처리 분석

아래 수치는 이 프로젝트의 `mac()` 함수를 개발 PC(Windows 11, Python 3.14.7)에서 **직접 측정한 값**입니다. 측정할 때마다 조금씩 달라질 수 있습니다.

### 5-1. 연산량

| 크기 | MAC 1회 곱셈·덧셈 횟수 (N²) | 측정 시간 (MAC 1회) |
|---|---|---|
| 100×100 | 10,000 | 0.9 ms |
| 500×500 | 250,000 | 24.1 ms |
| 1000×1000 | 1,000,000 | 101.5 ms |

- 500×500 → 1000×1000에서 연산 횟수는 4배, 측정 시간은 약 4.2배 늘어 O(N²) 증가와 일치합니다.
- 패턴 1개를 판정하려면 필터 2개(Cross, X)와 각각 MAC을 하므로 **200만 번 연산, 약 190 ms**가 걸렸습니다.
- 성능 분석에서 10회 반복 측정을 하면 1000×1000 한 크기에만 약 1초가 걸립니다. 패턴이 수천 개라면 판정만 수 분 단위가 됩니다.

### 5-2. 메모리 산정

| 저장 방식 | 1000×1000 표 1개 | 패턴 1개 + 필터 2개 |
|---|---|---|
| 이론값 (숫자 1개 = 8바이트) | 약 7.6 MB | 약 23 MB |
| 현재 방식: JSON에서 읽은 2차원 리스트 | **31.3 MB (측정)** | 약 94 MB |
| `array('d')` 1차원 배열 | **7.6 MB (측정)** | 약 23 MB |

- 파이썬 리스트는 숫자를 직접 담지 않고, 숫자 객체(1개당 24바이트)를 가리키는 주소(8바이트)를 담기 때문에 이론값보다 약 4배 큽니다.
- 소수점 셋째 자리 숫자로 채운 1000×1000 배열은 JSON 텍스트로만 약 6.6 MB입니다. 파일을 읽는 동안 텍스트와 리스트가 함께 메모리에 올라갑니다.

### 5-3. 우선 적용할 최적화 (우선순위 순)

| 순위 | 최적화 | 기대 효과 | 근거 |
|---|---|---|---|
| 1 | **한 번 순회로 두 필터 동시 계산 + 1차원 평탄화** | 시간 약 2.5배 단축 | 측정: 190 ms → 68~87 ms |
| 2 | **`array('d')`로 저장** (표준 라이브러리) | 메모리 약 4배 절감 | 측정: 31.3 MB → 7.6 MB |
| 3 | **블록화(타일링):** 큰 표를 작은 블록(예: 64×64) 단위로 나눠 계산 | 캐시 효율 향상, 블록 단위로 나눠 읽기 가능 | 순수 파이썬에서는 측정하지 않음. C나 NPU처럼 메모리 접근 비용이 큰 환경에서 효과가 큼 |
| 4 | **병렬화:** `multiprocessing`으로 행 구간을 CPU 코어마다 나눠 계산 후 부분합을 더함 | 코어 수에 비례한 단축 기대 | 측정하지 않음. 프로세스 시작과 데이터 복사 비용이 있어 작은 크기에서는 오히려 느릴 수 있음 |

- 1, 2번은 코드 수정이 작고 효과를 직접 확인했기 때문에 먼저 적용합니다.
- 이 중 **1차원 평탄화는 보너스 과제 1로 실제 코드에 적용**했습니다(6장). 두 필터 동시 계산과 `array('d')` 저장은 아직 적용하지 않았습니다.
- 3, 4번은 구조 변경이 크고 이 환경에서 측정하지 않았으므로, 적용 후 같은 입력·같은 반복 횟수로 전후 성능을 비교해 효과를 확인해야 합니다.
- MAC 연산은 칸끼리 서로 영향을 주지 않는 독립적인 곱셈의 합이라 나눠서 계산한 뒤 더해도 결과가 같습니다. 이 성질 때문에 블록화와 병렬화가 가능하며, NPU가 수천 개의 MAC을 동시에 처리하는 원리도 같습니다.

## 6. 보너스 과제 1 결과: 2차원 → 1차원 최적화

### 6-1. 무엇을 바꿨나요?

| | 최적화 전 (`mac`) | 최적화 후 (`mac_flat`) |
|---|---|---|
| 저장 방식 | 2차원 리스트 `pattern[row][col]` | 1차원 리스트 `pattern_flat[i]` (길이 N²) |
| 값 하나를 읽는 과정 | 줄(row)을 찾고 → 그 줄에서 칸(col)을 찾음 (2번 접근) | 번호 `i = row × N + col`로 바로 접근 (1번 접근) |
| 반복문 | 이중 반복문 (`for row` 안에 `for col`) | 단일 반복문 (`for i`) |
| 값 읽기 | `get_value()` 함수를 거쳐 읽음 | 리스트에서 바로 읽음 |

- 2차원 → 1차원 변환(`flatten`)은 측정 구간 밖에서 미리 해 두고, **MAC 연산 구간만** 비교했습니다.
- 두 방식의 점수는 data.json 6개 케이스 × 필터 2개, 총 12번 모두 **완전히 같은 값**이 나오는 것을 확인했습니다. 더하는 순서가 같기 때문에 부동소수점 결과도 같습니다.

### 6-2. 최적화 전/후 성능 비교 (같은 입력, 같은 반복 횟수 10회)

| 크기 (N×N) | 2차원 (ms) | 1차원 (ms) | 개선율 | 연산 횟수 (N²) |
|---|---|---|---|---|
| 3×3 | 0.0013 | 0.0006 | 51.6% | 9 |
| 5×5 | 0.0027 | 0.0010 | 63.9% | 25 |
| 13×13 | 0.0153 | 0.0055 | 64.1% | 169 |
| 25×25 | 0.0573 | 0.0231 | 59.7% | 625 |

※ 개선율 = (2차원 − 1차원) ÷ 2차원 × 100. 같은 프로그램을 3번 실행했을 때 개선율은 크기별로 약 33~64% 사이였습니다.

### 6-3. 결과 해석: 무엇 때문에 빨라졌나요?

빨라진 이유가 하나가 아니어서, 원인을 나누어 추가로 측정했습니다. (1000×1000, 3회 평균, 2번 실행)

| 방식 | 1000×1000 MAC 1회 |
|---|---|
| ① 2차원 + `get_value()` 함수 호출 (기존 `mac`) | 93.8 ~ 108.4 ms |
| ② 2차원 + 리스트에서 바로 읽기 (비교용) | 58.3 ~ 62.7 ms |
| ③ 1차원 (`mac_flat`) | 41.9 ~ 47.3 ms |

1. ① → ②: 칸마다 `get_value()` 함수를 부르는 비용이 사라져 약 40% 빨라졌습니다. 이건 메모리 접근보다는 **함수 호출 횟수(N²번 × 2)** 가 줄어든 효과입니다.
2. ② → ③: 같은 "바로 읽기"끼리 비교해도 1차원이 약 19~33% 더 빨랐습니다. 줄을 먼저 찾는 단계가 없어지고 반복문이 하나로 줄어든 **순수한 접근 단순화 효과**입니다.
3. 따라서 6-2 표의 약 60% 개선 중 일부는 함수 호출 제거 효과이고, 나머지가 1차원 접근 효과입니다.
4. 두 방식 모두 N²개의 칸을 한 번씩 계산하므로 **시간 복잡도는 똑같이 O(N²)** 입니다. 최적화는 계산 횟수가 아니라 **한 번 계산할 때 드는 비용**을 줄입니다.
5. 컴퓨터 메모리는 원래 번호(주소)가 한 줄로 이어진 공간이라, 1차원 배열은 메모리의 실제 모습과 같은 구조입니다. 또 번호 구간(예: 0 ~ N²/2, N²/2 ~ N²)으로 나누기 쉬워 5장의 블록화·병렬화로 확장하기에도 유리합니다.
